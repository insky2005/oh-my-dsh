# 需求 / 事项 存储（.dsh）

> 状态：演练期（无面板，agent / 人可直接读写）· 起始：2026-10-03
> 模型来源：`docs/research/ai-native-workflow-architecture.md`（需求 → 拆解 → 事项）

本目录是**项目共享的真实来源**：需求卡片与拆解出的事项落盘于此，随仓库提交；
面板与会话都只是读者 / 写者，不另立权威状态（架构文档原则 2：单一真相）。

## 布局

- `.dsh/requirements/REQ-<id>.md` —— 需求卡片（frontmatter + 正文）
- `.dsh/workstreams/WS-<id>.md` —— 事项（最小工作单元）
- `.dsh/workstreams/local.json`（**不提交**）—— 本机运行时绑定（会话 id 等）

## 写入策略（过渡）

- **当前**：无面板，agent / 人**直接读写**这些文件。
- **未来**：面板落地后改为**只能由面板写入**（单一写者 + 文件监听热重载），
  以消除「面板内存 board 覆盖外部改动」的冲突（见 `docs/design/panels/task-todo-skill-design.md:31`）。
- 因此现在写文件要**幂等、追加安全**，便于日后迁移。

## 不变量

1. 这些文件是权威；`.dsh/wiki` 是派生知识、可重建，**不得覆盖本目录**。
2. 需求只有池状态；它的「阶段」由子事项聚合派生，是视图不是权威。
3. 事项是最小工作单元；范围外新工作回流为新需求（只拆不胀，R5）。

## 与 .dsh/tasks 的关系

任务队列（`.dsh/tasks/*`）仍是「任务阶段」的载体；一个事项可关联 0..N 个队列。
两者不是同层实体：事项是追踪单元，队列是执行载体。
