## 0. 这份文档是什么

**主体**：本文描述的是 **oh-my-dsh 要实现的产品能力**——一套「AI 原生研发工作流」：需求池 → 拆解 → 事项的两层状态图、并行条件、载体与角色分工，以及支撑它们的工具清单。

**读者**：准备设计「流程面板 / 壳层能力」的人。相关设计文档应先与本文件的模型对齐。

**不是**：某个面板的设计文档；不含实现方案、接口字段、UI 细节。面板怎么做，由各自的 `docs/design/panels/*-design.md` 决定。**也不是本仓库自身的开发流程**——那是 `docs/process/*`。

**双重身份**：本仓库既是这套工作流的**实现者**（改 oh-my-dsh 时遵循 `docs/process/*`），又是它的**第一个用户（样板 / dogfooding）**。因此 §1 那次「多仓库工作区」开发，既是产品能力的**证据**，也是我们的日常。

**为什么先写它**：2026-10-02 的多仓库开发暴露了一个根本问题——我们（和业界）默认用一条**瀑布流水线**（想法 → 设计 → 任务 → 验收 → 交付）来理解研发过程，而真实过程是**有回环、有并行**的。模型错了，据此建造的面板必然建错。本文先把模型校准，再谈工具与面板。

## 1. 从一次真实开发看：瀑布模型错在哪

> 以下是一次真实使用（本仓库 dogfooding）的轨迹，作为产品模型的证据。

### 1.1 实际轨迹（2026-10-02）

| # | 事件 | 所处阶段 | 方向 |
|---|---|---|---|
| 1 | 「工作区根目录不是 git，任务面板识别不到」 | 想法 | — |
| 2 | 诊断 + 4 个绕过方案 | 想法 | — |
| 3 | 「如果产品化改造，你会怎么做」→ 方案 | 想法 | — |
| 4 | 起草设计文档 | 设计 | → |
| 5 | Q1–Q12 逐条往复 | 设计 | ⇄ 回环 |
| 6 | **Q6 由「根仓库优先」改为「根+子都参与」** | 设计 | ⇐ 推翻 |
| 7 | **模式判定由「按数量」改为「按位置」** | 设计 | ⇐ 推翻 |
| 8 | `/task-todo` 拆 6 条任务 + 建队列 | 任务 | → |
| 9 | 启动队列，跑到 6/6 报完成 | 任务 | → |
| 10 | 断网：P3/P4 实际未实现却被标 done | 任务 / 验收 | ✗ 误判 |
| 11 | 追加 3 条重跑 | 任务 | ⇐ 回环 |
| 12 | 交付前 5 轮 UI 反馈（radio→下拉→位置→文案→token） | 验收 → 实现 | ⇐ 回环 |
| 13 | 同期起草「任务完成校验」文档 | 设计（**另一事项**） | ∥ 并行 |
| 14 | 交付 → PR #75 | 交付 | → |

### 1.2 三个反例

1. **阶段会倒流**。设计阶段两度推翻既有结论（#6 #7）；执行阶段因失败重跑（#11）；验收阶段把实现打回重做（#12）。这些不是异常，是研发的常态。
2. **事项会并行**。「多仓库工作区」与「任务完成校验」两条线**同时推进、共用同一分支**（#9–#13）。
3. **工作区会被跨过**。多仓库事项天然横跨多个 git 仓库，工作发生在仓库之间，超出「一个工作区」的边界。

### 1.3 根因：追踪单元错了

瀑布模型隐含一个假设：**「工作区」是追踪单元，「工作区处于第几阶段」是状态**。这在三个反例面前全部不成立——一个工作区可以同时有多个事项、每个事项独立游走、还会倒流。

> **正确的追踪单元是「事项」，不是「工作区的阶段」。**

## 2. 核心概念

| 概念 | 定义 |
|---|---|
| **需求（Requirement）** | 追踪单元的**来源**：一条尚未确定做法的诉求，住在**需求池**（独立面板）。可拆出 1..N 个事项。需求有自己的池状态（候选 / 评估中 / 已拆分 / 挂起 / 丢弃），**不套用事项的阶段机**。 |
| **需求池（Idea Pool）** | 所有需求的家：收集、评估、拆分、丢弃。独立面板；「想法」升格后的实体容器。 |
| **拆解（Breakdown）** | 从需求到事项的**唯一入口**：agent 出第一版拆分方案，**人工确认**后生成 1..N 个事项，并留下「需求 → 事项」映射。 |
| **事项（Workstream）** | **最小工作单元**：一件有明确目标、可独立走完规划 / 设计 / 任务 / 验收 / 交付的工作。关联 1..N 个仓库/工作区、**0..1 个需求**（允许不挂需求）、通常 1 份设计文档、1 个队列、1 个 PR；超出即应拆成多个事项。 |
| **阶段（Stage）** | 事项所处的**状态**，不是「必须依次经过的站点」。阶段之间有向图，允许回边、允许跳过、允许停驻。 |
| **规划（Planning）** | 事项的首个阶段：定 WHAT / 边界 / 验收标准，并声明**裁剪掉哪些后续阶段**（R3）。不写实现方案。 |
| **验收标准（Acceptance）** | 规划阶段的完成证据：可机检的通过判据 + 被裁剪阶段的声明。 |
| **裁决（Verdict）** | 验收的**点记录**：判定人 + 证据 + 覆盖的那次变更。判定后永不「失效」；后续改动只是**未被它覆盖**。 |
| **覆盖（Coverage）** | 裁决只覆盖它裁定的那次**变更**（不可变内容标识）；验证义务跟随**引入改动的事项**，不跟随文件。 |
| **回归门（Regression Gate）** | 长期必须成立的验收标准，从「点记录」升级为**每次改动都跑**的检查；后事项打破它 → 是后事项失败，不是前事项重开。 |
| **交付结果（Outcome）** | 交付阶段的可观测结果：`open`（评审中）/ `merged` / `closed`（未合关掉）/ `abandoned`。由 PR 状态派生，或放弃时显式记录。 |
| **终态（Terminal）** | **派生谓词，不是 stage**：`stage == 交付` 且交付结果终结（merged / closed / abandoned）→ closed。观察得到，不手写、不回弹；重开另起事项并回指。 |
| **回边（Back-edge）** | 从较后阶段返回较前阶段的合法迁移：设计返工、执行重跑、验收退回、交付后反馈。 |
| **工作树（Worktree）** | 事项的**物理隔离单元**（git worktree）。一个事项 = 每目标仓库一个工作树 + 一条分支。 |
| **工作台（Workbench）** | 面板在流程中的**角色**：展示并处理「处于某个阶段的**所有**事项」，跨工作区、跨队列。 |
| **载体（Carrier）** | 阶段内实际干活的工具：对话 / 文档 / 面板 / 会话。 |
| **追溯（Trace）** | 需求 → 拆解 → 事项 → 决策 → 任务 → 提交 → PR 的因果链，含回边与回池历史。 |
| **角色（Role）** | 每个阶段的「谁出第一版 / 谁校验 / 谁负责」：Delegate（agent 首版）、Review（人校验）、Own（人负责）。见 §3.6。 |
| **产物（Artifact）** | agent 可用的指令产物四类：rules / specs / workflows / skills。见 §10.5。 |

> **与上一版的关系**：本文 v1 把「想法」当作事项的第一个阶段；现已把它升格为独立实体（需求），事项的首个阶段改为「规划」。§1.1 轨迹里的「想法」事件，按新模型对应「需求 + （后来的）拆解」。

## 3. 工作流架构

### 3.1 需求 → 事项 的两层状态图

```
第一层：需求池（需求各自独立状态，不进事项阶段机）

  ┌──────┐   ┌────────┐   ┌────────┐        ┌──────┐
  │ 候选  │──►│ 评估中  │──►│ 已拆分  │        │ 挂起  │
  └──────┘   └────────┘   └───┬────┘        └──────┘
                              │ 拆解：agent 出方案 / 人工确认
                              ▼ 生成 1..N 个事项

第二层：事项（最小工作单元，各自独立状态）

  ┌──────┐   ┌──────┐   ┌──────┐   ┌──────┐   ┌──────┐
  │ 规划  │──►│ 设计  │──►│ 任务  │──►│ 验收  │──►│ 交付  │
  └───┬──┘   └───┬──┘   └───┬──┘   └───┬──┘   └───┬──┘
      │          │          │          │          │
 裁剪/退回   设计返工   执行重跑   验收退回   交付反馈
                 ▲                     │
                 └─────────────────────┘
                       验收退回设计

  ∥ 并行  同一需求拆出的多个事项同时处在不同阶段
  ⊘ 跳过  小事项：规划时声明裁剪 → 直接进任务 / 交付
  ■ 停驻  待确认：验收侧的暂挂态（不是终点）
  ⬛ 终态  派生：交付结果终结（merged / closed / abandoned）→ closed；是谓词不是 stage
         交付 --outcome--> open(评审中) / merged(已交付) / closed / abandoned
  ↩ 回池  事项发现范围外问题 → 回流需求池 → 另起事项（只拆不胀）
  ＊ 需求层的「阶段」是由子事项派生的聚合视图，不是权威状态
```

### 3.2 阶段的六条规则

| # | 规则 | 含义 |
|---|---|---|
| R1 | **阶段是状态，不是站点** | 面板不该被设计成「流程的第 4 站」，而应是「某状态的工作台」 |
| R2 | **回边合法，且必须留痕** | 返工 / 退回 / 重跑是正常工序，但要有记录，否则追溯链断裂 |
| R3 | **阶段可跳过，但必须在规划声明** | 裁剪发生在**规划**阶段（纯调研无交付、小修复无设计），声明本身是规划产物 |
| R4 | **阶段可停驻** | 「待确认」是一等状态，可停留、可回退，不得被当作成功 |
| R5 | **只拆不胀** | 事项是最小工作单元；范围外的新工作回流需求池、另起事项，不得就地吸收 |
| R6 | **需求不套阶段机** | 需求只有池状态；它的「阶段」由子事项聚合派生，是视图不是权威 |
| R7 | **终态是派生谓词** | closed = `stage == 交付` 且交付结果终结（merged / closed / abandoned）；是**观察**不是**迁移**，故不手写、不来回翻转；重开另起事项 |

### 3.3 三种并行

| 粒度 | 说明 |
|---|---|
| **事项级** | 同一工作区内，多个事项同时推进（本案例 #13） |
| **工作区级** | 多个工作区同时推进，互不干扰（项目面板的列表天然表达） |
| **仓库级** | 一个事项横跨多个 git 仓库（多仓库工作区） |

同一需求拆出的多个事项，天然是「事项级并行」的候选——这也是把大需求拆开的收益：不拆，就只能在一个事项里串行。

### 3.4 并行的三个必要条件

并行不是「同时开两个任务」那么简单。缺任何一块，都是**假并行**：

| # | 条件 | 作用 | 缺失的后果 |
|---|---|---|---|
| **A. 隔离** | 每事项独立工作树（git worktree） | 分支与文件互不干扰 | 分支来回抖、未提交改动互相覆盖 |
| **B. 调度** | runner 能同时推进 N 个队列 | 真正并发执行 | 有隔离但跑不起来（当前为单相位机、单 active 队列） |
| **C. 归并** | 分叉后 rebase/merge，冲突可暴露 | 收敛回主干 | 各干各的，交付时才发现无法合并 |

> 当前实现：A、B、C **三者皆无**。其中 A（worktree）是地基，但它单独不够。

### 3.5 四种载体及其分工

| 载体 | 擅长 | 不擅长 |
|---|---|---|
| **对话** | 发散、探索、拍板、细粒度迭代 | 留存、门禁、跨会话协调 |
| **文档** | 决策与设计的**留存**、可追溯 | 状态跟踪、门禁 |
| **面板** | 状态跟踪、门禁、跨事项协调 | 发散、早期模糊 |
| **会话** | 阶段内的执行 | 跨阶段、跨事项 |

一句话：**对话负责发散与拍板，文档负责留存依据，面板负责收敛 / 追踪 / 门禁，会话负责阶段内执行。**

### 3.6 角色分工：Delegate / Review / Own

阶段之外，每一阶段的工作都要明确三种角色（OpenAI 指南贯穿全程的结构，见 §10）：

| 角色 | 谁 | 做什么 | 落在哪 |
|---|---|---|---|
| **Delegate** | agent | 出第一版：分析 / 实现 / 测试 / 审查 / 文档 | 会话、面板 |
| **Review** | 人 | 校验、纠偏，补足 agent 看不到的约束 | 验收工作台、审查面板 |
| **Own** | 人 | 架构、产品意图、质量与最终 sign-off | 设计决策（ADR）、交付门禁 |

**拆解同样走 Delegate / Review**：agent 出第一版拆分方案（哪些事项、边界、依赖顺序），人做 Review 后确认；需求拆成 1..N 个事项的动作，人保留拍板权。

**Review 与 Own 必须分开**：阶段里可以有 agent 的第一版，也可以有人工校验，但「谁为结果负责」永远是人，且**校验动作不自动等同于负责**。

## 4. 工具集

> 状态图例：**成熟** = 已实现且够用；**在途** = 已有草案未实现；**缺失** = 尚无。

### 4.1 想法 / 需求阶段

| 工具 | 目的 | 现载体 | 状态 | 缺口 |
|---|---|---|---|---|
| 对话 | 发散、定义问题、列候选方案 | dsh 会话 | 成熟 | — |
| 需求池面板 | 需求的家：收集 / 评估 / 拆分 / 丢弃 | 无（**独立面板**，设计未立项） | **缺失** | 需求无家，散落对话与文档 |
| 想法收件箱 | 把对话中的想法落成**需求卡片** | 无 | **缺失** | 想法不进结构，只活在对话里 |
| 拆解器 | agent 出「1 需求 → 1..N 事项」方案，人工确认 | 无 | **缺失** | 需求到事项无入口；人工拆分不可复现 |

> 需求池面板的设计文档（未建）：`docs/design/panels/requirements-pool-panel-design.md`。

### 4.2 规划阶段

| 工具 | 目的 | 现载体 | 状态 | 缺口 |
|---|---|---|---|---|
| 验收标准 | 定「怎么算完」：可机检的通过判据 | `docs/design/panels/planning-template-design.md` | **在途** | 门禁未落地（WS-008 / `REG-002`） |
| 阶段裁剪声明 | 声明本事项走哪些后续阶段（R3） | `docs/design/panels/planning-template-design.md` | **在途** | 门禁未落地（WS-008 / `REG-002`） |
| 需求回指 | 事项可选地回指来源需求 | 无 | **缺失** | 需求 → 事项的映射无处存 |

> 规划阶段的**完成证据** = 验收标准 + 被裁剪阶段的声明；没有这两样，不进设计。

### 4.3 设计阶段

| 工具 | 目的 | 现载体 | 状态 | 缺口 |
|---|---|---|---|---|
| 设计文档 | 方案与取舍留存 | `docs/design/**` + 文件面板 | 成熟 | 状态字段靠手写 |
| 设计评审 | 逐条拍板「待确认问题」 | 对话 | **在途** | Q 表须人工解析，多轮往复易错 |
| 决策记录（ADR） | 决策 + 理由 + 被否方案 | 无 | **缺失** | 理由散落对话，易绕回老方案 |

### 4.4 任务阶段

| 工具 | 目的 | 现载体 | 状态 | 缺口 |
|---|---|---|---|---|
| 队列 / 任务 | 拆分、排序、执行 | 任务面板（IssueRunner） | 成熟 | — |
| 会话 | 每任务一次执行 + 回传 | 任务队列 × 会话回传 | 成熟 | — |
| 工作树（worktree） | 事项物理隔离 | 无 | **缺失** | 并行的前提（§3.4-A） |
| 并发调度 | N 队列同时推进 | 无 | **缺失** | 当前单相位机 + 单 active 队列（§3.4-B） |
| 任务级计划（PLAN） | 单个**任务**的实施计划，随任务提交；与事项的「规划」阶段、需求的「拆解」是三个不同层级，勿混 | 无 | 可选 | 业界用 `PLAN.md`；我们可由任务正文承载 |

### 4.5 验收阶段

| 工具 | 目的 | 现载体 | 状态 | 缺口 |
|---|---|---|---|---|
| 完成校验 | 会话结束 ≠ 任务完成（marker + 待确认） | 草案 | **在途** | 未实现，误判完成 |
| 测试优先门 | 新测试必须**先失败**，再改实现；测试与实现分开生成 | 无 | **缺失** | 防「测试迁就实现」（见 §10.4） |
| 审查证据 | 会话改动逐行审计（只读） | 审查面板 | 成熟 | 未接入验收 |
| 证据产物 | 测试输出 / diff / 验收结论落盘，跨会话可开 | 无 | **缺失** | 证据不随会话消失 |
| 裁决记录 | 验收 = 点记录（判定人 + 证据 + 覆盖的变更），不可变 | 无 | **缺失** | 勿做成「内容一变即失效」的实时谓词（F7/F8 的教训） |
| 回归门 | 长期不变量每次改动都跑；后事项打破 → 后事项失败 | 无 | **缺失** | 现无回归，前事项会被误要求重验 |
| 验收工作台 | 声明 vs 证据，逐条通过 / 退回 | 无 | **缺失** | 核心缺口，且交付未与之门禁 |

### 4.6 交付阶段

| 工具 | 目的 | 现载体 | 状态 | 缺口 |
|---|---|---|---|---|
| 交付（push / PR） | 面板 finalize 会话 | 任务面板 | 成熟 | 与验收脱钩（无门禁） |
| 发布 | 版本发布流程 | 无（样板：`docs/process/release-process.md`） | **缺失** | 产品尚未提供发布能力 |
| 交付追踪 | PR / CI / review / merge 生命周期 | 无 | **缺失** | 交付后状态无家 |
| 交付结果派生 | 由 PR 状态派生 outcome（open/merged/closed）；closed 为谓词 | 无 | **缺失** | 手写 closed 会来回翻转；应观察而非迁移 |
| 运维 / 可观测 | 日志 / 根因（业界用 MCP 接日志系统） | 无 | 暂不纳入 | 超出壳层范围（§10.6） |

### 4.7 横切

| 工具 | 目的 | 现载体 | 状态 | 缺口 |
|---|---|---|---|---|
| 追溯链 | 本模型：需求 → 拆解 → 事项 → 决策 → 任务 → 提交 → PR；业界标准链：principles → … → tests | 无 | **缺失** | 底座；缺它则各面板各说各话 |
| 评测集 | 金标准 PR / 用例，度量 agent 产出质量 | 无 | **缺失** | 「唯一会复利的资产」的评审版 |
| 生命周期总览 | 跨工作区看「卡在哪」 | 项目面板（可承载） | 部分 | 现按工作区目录组织，无流程语义 |
| 知识库 | 沉淀 | Wiki 面板 | 成熟 | 未与事项关联 |
| 快照回退 | 会话级回退 | 壳层 | 成熟 | — |

## 5. 载体分工判据：什么时候该用面板

| 维度 | 留给对话 | 值得面板化 |
|---|---|---|
| 状态 | 无 / 一次性 | 有明确阶段迁移 |
| 产物 | 只存在于当下 | 要长期留存、要追溯 |
| 证据 | 无需审计 | 需要门禁 / 证据链 |
| 重复性 | 一次性 | 反复发生、模式稳定 |
| 交互粒度 | 细、需逐步反馈 | 粗到「选一个 + 提交」 |
| 参与者 | 单人即时 | 跨会话 / 跨时间 |

**反例（不要面板化）**：发散与方案探索、需人眼逐轮的细粒度迭代（本案例的 5 轮 UI 反馈就是好例子）、一次性无状态确认、文档早期模糊草稿。

## 6. 现状与缺口总览

```
需求池 ──[收件箱]──► 需求 ──[拆解：agent 拆 / 人确认]──► 事项
  ✗ 池面板            ✗ 收件箱          ✗ 拆解器                    │
                                                                    ▼
  规划 ──[文档]──► 设计 ──[文档]──► 任务 ──[面板]──► 验收 ──[?]──► 交付 ──[面板]──►
  ✗ 验收标准/裁剪   ✗ ADR/评审      ✓ 队列/会话      ✗ 工作台       ✓ 交付
                    ✓ 设计文档      ✓ wiki           ✗ 完成校验     ✗ 交付追踪
                    ─────────────────────────────  ✗ 审查未接入
        ✗ 追溯链（需求 → 拆解 → 事项 → …，贯穿全程，缺失）   ✗ worktree/并发（并行前提，缺失）
```

**缺口集中在两端**：前端（想法、设计的决策留存）与后端（验收、交付门禁）。中段（任务执行）最成熟。

## 7. 架构原则

1. **以事项为最小追踪单元**，需求是它的来源、不单独设阶段机；不以工作区阶段为单元；
2. **单一真相**：当前工作区、事项状态各自只有一个权威来源，面板不引入第二套状态；
3. **完成必须有可机检证据**：不接受「会话结束 = 任务完成」这类无证据判定；
4. **回边必须留痕**：返工、退回、重跑要进追溯链；
5. **面板是工作台，不是站点**：一个面板服务一个**阶段**，聚合跨工作区的事项；
6. **并行以隔离为前提**：没有独立工作树，就不宣称并行；
7. **壳层只编排，不改 dsh 源码**：复用 dsh 既有能力，扩展走壳层面板 + 会话；
8. **裁决是点记录，不是实时谓词**：验收结论锚定**被裁定的那次变更**（不可变内容标识）；判定后永不「失效」，后续改动只是**未被该裁决覆盖**，由新事项裁定；
9. **门要能自证**：任何判定都要能用负例证明它会失败，否则「绿」不算数；
10. **测试 / 评测是第一资产**：验收以可执行测试与评测集为准，而非叙述；
11. **只拆不胀**：事项不因发现新工作而变大，范围外工作回流需求池、另起事项；
12. **需求状态是派生的**：需求层的「阶段」只是子事项的聚合视图，不引入第二套权威状态；
13. **拆解 agent 出方案、人确认**：拆分可复现、可追溯，人保留拍板权；
14. **不变量回归，点事件记录**：长期必须成立的验收标准升级为回归门（每次改动都跑）；一次性裁决只作证当时那次变更；
15. **终态是派生的，不是迁移**：closed = `stage == 交付` 且交付结果终结；由 PR 状态观察得出，不手写字段、不来回翻转；重开另起事项并回指。

## 8. 演进依赖（先后关系，非排期）

```
需求池 + 收件箱 ──► 拆解器（agent 拆 / 人确认）──► 事项（1..N）
                                                     │
        完成校验（产生可机检的「待确认」） ◄───────────┘
        │
        ▼
   验收工作台 ──► 交付门禁
        │
        ├──────────────► 追溯链（需求 → 拆解 → 事项 → 决策 → 任务 → 提交 → PR）
        │                     │
        ▼                     ▼
   设计决策 / ADR ──────► 生命周期总览（项目面板）
                              ▲
   worktree + 并发调度 ────────┘（并行的物理前提）
```

- **追溯链是底座**：不先有它，验收工作台与总览只能各说各话；
- **完成校验是验收的前置**：没有可信的「待确认」，验收无对象；
- **worktree 是并行的前提**：没有它，事项只能串行，总览也就退回成一条流水线；
- **拆解器是需求侧的前提**：没有它，大需求只能变成大事项，前面两条收益都吃不到。

## 9. 开放问题

| # | 问题 | 说明 |
|---|---|---|
| Q1 | 事项如何标识？ | 由拆解显式生成（可回指需求）；无需求的事项如何自证身份？本案例的锚点是 `feature/multi-repo-workspace` + 设计文档 + 队列 + PR |
| Q2 | 阶段状态的权威来源在哪？ | 由各载体上报（队列文件、文档状态字段、标记），还是壳层集中维护？ |
| Q3 | 并行的资源上限？ | N 个会话 / agent / 工作树，需要最大并行数 |
| Q4 | 无 git 工作区的降级？ | plain 工作区没有 worktree，只能串行，需明确语义 |
| Q5 | 多人协作时事项归属？ | 目前所有设计都假设单用户、单机 |
| Q6 | 验收标准是否必须落成可执行测试 / 评估？ | 否则无法机器校验，退化为叙述 |
| Q7 | 评测集从哪来、怎么维护？ | 金标准 PR / 用例；需长期积累与版本化 |
| Q8 | 裁决失效的粒度？ | **已定（纠偏）**：裁决是**点记录**，锚被裁定的那次**变更**（不可变 blob/tree），不锚分支 / 裸 commit / 文件当前内容；不存在「失效」，只有「未覆盖」。见原则 8 / 14 |
| Q9 | 拆到什么粒度算一个事项？ | 1 设计 + 1 队列 + 1 PR 是判据还是经验值？agent 拆解、人工确认的界面与回退规则 |
| Q10 | 无需求的事项怎么追踪？ | 事项允许不挂需求（小修复 / 顺手活）；它们如何进入生命周期总览而不丢 |
| Q11 | 需求池与项目面板如何分工？ | 「需求池」独立面板 vs 「项目面板」生命周期总览，是否会出现两套列表 |
| Q12 | 回池的边界？ | 验收发现的问题，什么算「范围外 → 回流」，什么算「本事项没做完 → 回边」 |
| Q13 | 多事项共编同一文件时的覆盖粒度？ | 覆盖锚到**变更（diff）**而非文件整体：谁引入的改动谁负责。跨事项长期成立的部分升级为回归门；是否还需 hunk 级归属，待定 |
| Q14 | 需求何时算关闭？ | **已定**：关闭是**派生谓词**——`closed(req) = children(req) ≠ ∅ 且 ∀ ws ∈ children(req): terminal(ws)`，其中 `terminal(ws) = stage == delivery 且 delivery.outcome ∈ {merged, closed, abandoned}`；部分交付也算关闭，空子集不自动关闭，`discarded` 为显式放弃；关闭不回弹，重开另起需求并回指。见原则 15 / 设计 §6（REQ-003） |
| Q15 | 事项终态与重开规则？ | **已定（纠偏）**：终态是交付结果的**派生谓词**（stage=交付 且 outcome 终结），不是 stage；由交付追踪观察 PR 状态。重开另起事项并回指 |

## 10. 业界对照：AI Native Engineering

> 本节把外部的实践与研究对齐到上面的模型，作为校准依据；结论已并入 §2 / §3.6 / §4 / §7 / §9。

### 10.1 对照来源

| 派别 | 代表 | 主要贡献 |
|---|---|---|
| **实践指南** | OpenAI《Building an AI-native engineering team》 | 七阶段 SDLC + **Delegate / Review / Own**；测试先必须失败 |
| **宣言** | AI-Native Engineering Manifesto | 11 条硬道理：模型无状态、上下文选择、测试库复利 |
| **学术 / 流程** | Spec-Driven Agentic Development（GitHub Spec Kit） | 四类产物 + 六阶段生命周期 + 追溯模型（principles → … → tests） |
| **工具 / harness** | vteam-harness | done 是退出码、**裁决绑定 commit**、证据树、门要能自证 |

### 10.2 被验证的共识（我们没走偏）

1. **外部化状态 = 对抗模型无状态**：模型本身无记忆，可靠的东西必须落到外部（文档 / 面板 / 证据）；
2. **完成必须可机检**：业界共识是「exit code / 证据」，不是「agent 说完成了」；
3. **agent 出第一版，人 own 架构与质量**：Delegate / Review / Own 与我们的载体分工同构；
4. **上下文选择是核心能力**：重点不是生成，而是「喂什么进上下文」；
5. **并行靠隔离**：独立工作树（worktree）是并行 agent 的前提。

### 10.3 我们更准的地方

| 维度 | 业界普遍 | 我们 |
|---|---|---|
| 流程形态 | 线性阶段（SDD 六阶段 / OpenAI 七阶段） | **事项状态图**，含回边、跳过、停驻 |
| 追踪单元 | feature / PR | **事项**（可并行、可跨仓库） |
| 仓库假设 | 单仓库 | **多仓库工作区** + worktree × 仓库矩阵 |
| 状态宿主 | AGENTS.md + 文件 + 工具约定 | **常驻壳层面板**（状态与门禁有家） |

### 10.4 值得吸收的硬做法

| # | 做法 | 来源 | 落点 |
|---|---|---|---|
| 1 | **裁决绑定 commit**：代码一动，验收作废 | vteam | §7 原则 8 |
| 2 | **门要能自证**：用负例证明它会失败 | vteam | §7 原则 9、§4.5 |
| 3 | **测试先必须失败**，测试与实现分开生成 | OpenAI | §4.5、§7 原则 10 |
| 4 | **证据产物跨会话留存**，不随会话消失 | vteam | §4.5 |
| 5 | **评测集是复利资产**（金标准 PR / 用例） | 宣言、OpenAI | §4.7、§9 Q7 |
| 6 | 每阶段明确 **Delegate / Review / Own** | OpenAI | §3.6 |
| 7 | 任务级 **PLAN** 随任务提交 | OpenAI | §4.4 |

### 10.5 产物的四类命名

业界把 agent 可用的指令产物分为四类。本仓库（作为样板）四样**都有**，只是从未并列命名——命名之后，「一条新规范该做成什么」就有据可依：

| 类型 | 作用 | 本仓库的对应（样板） |
|---|---|---|
| **rules** | 长期约束 | `AGENTS.md` |
| **specs** | 本次要做什么 | `docs/design/*-design.md` |
| **workflows** | 可复用流程 | `docs/process/*` |
| **skills** | 可调用能力 | `.dsh` skills |

### 10.6 我们明确不做的

- **运维 / 可观测**（Deploy & maintain）：壳层聚焦开发工作站，暂不纳入（§4.6 已标注）；
- **社交式评审门禁**：我们走**机械门禁**（证据 + commit 绑定），而不是「相信我，我审过了」。
